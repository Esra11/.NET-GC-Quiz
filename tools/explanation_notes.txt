1|Think of memory management and resource management as separate jobs. A FileStream object occupies managed memory but also owns an operating-system handle. Collecting the wrapper is not a good way to schedule closing the file: use using or Dispose for timely cleanup. GC also cannot fix an unwanted object that your static cache still strongly references.
2|Eligible does not mean already deleted. The runtime must finish the necessary collection processing before reclaiming space. A variable going out of scope, assigning null, or calling Dispose removes no other references automatically. For a finalizable object there is an additional step: it can remain alive long enough for finalization before a later collection reclaims it.
3|This is a blocking compacting collection path, not a requirement that every GC execute four identical passes. After marking, planning may choose a nonmoving sweep instead. Relocation means repairing references to destinations, while compaction means physically moving bytes. A single collection can choose different treatment for different heap areas.
4|The object graph is not built from scratch by GC: application allocations and reference assignments have already created its nodes and edges. Marking discovers the portion reachable from roots. An object not marked halfway through traversal may simply not have been reached yet; that state alone does not prove it can be reclaimed.
5|Planning considers more than whether the next requested object fits. It can consider free-space distribution, moving cost, pinned survivors and memory pressure. A noncompacting collection still needs to determine how usable free space will be recovered. Do not assume that all planning can run concurrently just because its eventual result might be sweeping.
6|For example, live A, dead gap, live B can become live A followed by live B after compaction. With sweeping, the gap remains between them but can satisfy an allocation of a suitable size. Neither operation automatically runs Dispose. Freeing gaps also does not guarantee that Windows receives those pages immediately.
7|Suppose B will move from address 1000 to 800. A field holding a tracked reference to B must be changed to B's destination; the same principle applies to a root in a stack slot, register or handle. This is not just updating a lookup table. Moving compaction coordinates application suspension while references and object locations are repaired.
8|For example, a full collection might compact small-object areas while sweeping the LOH. Pins can constrain movement even within an area selected for compaction. Therefore, 'mark, plan, then sweep or compact' is a useful overview, but sweeping versus compaction need not be one global either/or decision for the whole process.
9|A thread can reach the end of its allocation context and obtain another range without collecting. If budgets or memory availability require collection, GC then begins the applicable tracing and reclamation work. The trigger and the phases are different ideas: allocation can trigger a GC, but allocation is not itself the mark phase.
10|This refers to managed heap allocations, not a claim that every C# value requires a heap allocation. Struct values may be inline in another object or live in stack/register storage. A JIT optimization can also eliminate some allocations. For a normal small object that really is heap-allocated, generation 0 is the usual starting point.
11|Generation collection is inclusive of younger generations: a generation 1 collection covers 0 and 1, and a full generation 2 collection covers the ordinary younger generations too. LOH and POH have their own heap organization and are collected with generation 2 work. Background collection changes scheduling, not the basic meaning of generation membership.
12|The rule 'every survivor advances a generation' has an upper limit and implementation-specific exceptions. Generation 2 survivors cannot advance beyond generation 2. Being kept through a background collection is not necessarily a new promotion event either. Survival, generation membership, pinning and physical movement are related but separate properties.
13|A → B → A is just a cycle of edges. GC needs an entry path from a root, such as a live local, static field or strong handle, to establish that the cycle is reachable. Reference counting would have a particular difficulty with cycles; .NET tracing GC does not rely on reference counts to decide ordinary reachability.
14|A finalizer does not automatically call your public Dispose method. It executes the finalizer body the developer supplied, which may explicitly call Dispose(false). A using statement invokes Dispose deterministically at scope exit. Running either cleanup method does not erase a managed instance immediately; GC handles its storage separately.
15|For example, allocating 500 MB per second can coexist with a stable 50 MB live heap when most objects die quickly. Conversely, modest allocation can slowly fill a static dictionary that retains everything. The first problem suggests examining allocation hotspots and collection cost; the second suggests examining roots, cache policy and object ownership.
16|There are several layers: dead object space becomes reusable by GC; some pages may remain committed; some may be decommitted; an address reservation may later be released. These actions are not interchangeable. A process memory counter may stay high after collection because the runtime deliberately keeps capacity for future work.
17|Promotion is about surviving the collection that examines the object, not simply waiting for time to pass. A rooted object may survive, while a short-lived temporary dies in generation 0. Do not infer that all generation changes copy bytes: nonmoving paths and pinning-related policies can leave addresses unchanged.
18|A generation 0 object can remain there until a relevant collection occurs, even if it has existed for a long wall-clock interval. Conversely, rapid collections can promote an object quickly. This distinction matters when interpreting dumps: an old generation suggests collection history, not a reliable construction timestamp. Generation number is not an object-age clock.
19|In a segment-based heap layout, boundaries can be adjusted on nonmoving paths; other runtime layouts use different metadata. This is not arbitrary relabeling of scattered survivors without rules. Ordinary young-generation collection is paused, so application threads cannot allocate new objects while those paused boundary changes are taking place.
20|Stop-the-world means the relevant managed application execution is suspended for the collection. It does not mean every native OS thread must be doing identical work. Background generation 2 marking can be interrupted for a foreground young collection, after which application threads and background work continue.
21|A young heap with many survivors and reference fields takes more work than one whose objects mostly die. Root scanning, pins and coordination also add cost. Calling these collections 'usually fast' describes a common workload pattern, not a contract. Measure pause duration under representative load rather than relying only on the generation label.
22|Imagine background generation 2 marking is running while requests keep allocating. Generation 0 fills, a blocking young collection runs, then execution resumes and background work continues. Newly allocated objects are handled by the runtime's background-GC protocol; they are not simply reclaimed because an earlier traversal did not mark them. The whole interval is not one uninterrupted pause.
23|If rooted old object A points to new object B, collecting only young memory must still discover B. Tracking old regions with potentially young references avoids tracing the entire old graph every time. The write barrier is runtime/compiler-generated reference-store bookkeeping, not code developers normally call explicitly after each assignment.
24|An object's new generation does not rewrite all its children's generations automatically. If A becomes older while B remains younger, A's reference to B still matters at B's next young collection. The collector maintains suitable remembered information; promotion does not mean it can forget all outgoing references from the survivor.
25|Some GC implementations adjust generation membership to accommodate layout around pinned objects. A survivor may remain classified in a younger generation instead of being promoted in the usual way. That does not mean it became unreachable or its address moved backward. Treat this as an implementation detail rather than assuming every current GC layout uses the same policy.
26|Typically the fast small-object path uses generation 0 allocation space assigned to the thread. It is a range and a pair of positions, not a table of all objects owned by that thread. You do not replace the GC by using an allocation context in application code; the runtime uses it underneath ordinary allocation expressions.
27|A shared allocation pointer would need coordination whenever multiple threads tried to advance it. Giving each thread a distinct range avoids that contention on the common fast path. A shared lock here means synchronization around shared allocator state, not the GC mark stack or a COM apartment. Getting a fresh range is a different, slower operation.
28|For example, with pointer 1000, limit 2000 and an aligned allocation of 40 bytes, the allocator can use the next space and advance the pointer. The exact addresses are illustrative. The pointer is allocator state, not an object that is 'built during compaction'; compaction can help create contiguous space that this allocation strategy can use.
29|The slow path may refill a context, acquire or commit space, or trigger GC, depending on runtime state. Therefore, an exhausted context is not proof of memory exhaustion. Also distinguish its current limit from the generation's adaptive collection budget: these are related allocator/GC policies, not one universal threshold.
30|Higher budget usually means allowing more bytes before that budget-driven trigger, so collections may occur less often. It is not lowering the threshold, reserving the same amount of physical RAM, or guaranteeing no GC until that exact count. Other constraints, including pressure and explicit requests, can cause collection earlier.
31|If many objects survive, repeatedly collecting a tiny budget can scan and move much data for little reclaimed space. A larger budget can improve efficiency. Other objects may still die, but the policy weighs their reclamation against collection cost and memory constraints; high survival alone is neither proof of a leak nor the only input.
32|For instance, two 600-byte gaps separated by a live object do not satisfy one contiguous 1,000-byte allocation, even though their sum is 1,200. Compaction can reduce such gaps when movement is allowed. Fragmentation can exist in any area that has not been effectively compacted, not only where an object is pinned right now.
33|A 100-byte request might use a 160-byte free block and leave a reusable remainder if the allocator's representation and minimum sizes permit it. Sweeping can build reusable free-space structures; allocation then consumes them. Bump pointers and free lists are allocation mechanisms, not themselves names of GC collection phases.
34|A heap walker must know how many bytes to skip between valid live objects. Representing a free gap in a recognized format permits that traversal and later reuse. Seeing Free in a heap-statistics table therefore does not mean there is a user-defined object of that size holding application data or a finalizer waiting to run.
35|For an array, object header and array overhead count toward the allocation size, so payload length alone is not the full test. The threshold is normally expressed in bytes, not '85 KB of elements' regardless of element type. LOH membership also does not mean the object is pinned or cannot ever move.
36|Young-generation collections happen frequently because most small objects die quickly. Moving large survivors during each such cycle would consume memory bandwidth for little benefit. Separating the LOH changes collection policy; it is not a claim that a large array has no references or is unmanaged memory. Reference-containing large arrays still need appropriate GC tracing.
37|A full collection can perform different reclamation work in each area. The phrase 'generation 2 includes LOH collection' does not mean LOH is physically the same contiguous range as ordinary generation 2 objects. Likewise, a large array is not allocated in generation 0 first and promoted through every generation.
38|For example, setting GCSettings.LargeObjectHeapCompactionMode to GCLargeObjectHeapCompactionMode.CompactOnce requests LOH compaction on the next applicable full blocking collection. It is not a guarantee that a background collection will move LOH objects concurrently. Pinned objects can still constrain movement, and requesting compaction is not a routine substitute for fixing excessive allocation.
39|Even if allocation-pointer advancement is cheap, preparing a very large array is real memory work. Clearing reference-containing storage is also essential for correct tracing and safe default values. Pooling may avoid repeated allocation/initialization costs in some cases, but borrowers must not assume returned buffers are already cleared.
40|ArrayPool<T>.Shared.Rent(size) can provide a reusable array, often at least the requested length. Use only the intended logical portion and return it in a finally block when finished. Pooling trades fewer allocations for retained reusable capacity; it does not imply the process's memory counter will instantly shrink.
41|The pool may hand the same array to another request immediately after Return. A local variable still referencing that array does not preserve exclusive ownership. This is a use-after-return ownership bug, even though GC memory safety may keep the managed array allocated. Do not retain slices or references for later use after returning it.
42|For reference-element arrays, stale entries can keep an entire graph alive while the pool retains the array. For byte or character buffers, old contents can disclose secrets to a later borrower. Select an appropriate clearing policy, such as Return(array, clearArray: true), while accounting for the CPU cost of clearing.
43|A root is an entry point for tracing. An instance field is normally an outgoing edge, so it only helps if GC reaches the object containing it. Root categories include reported live stack/register references, static storage and strong runtime handles; finalization machinery can also retain graphs. Weak handles have different reachability rules.
44|For example, static List<Customer> cache can retain every Customer added to it even after each request finishes. The list's elements can retain still more objects. Making the variable static does not pin these objects; GC may move them while keeping references correct. Unbounded rooted collections are a common managed-memory leak pattern.
45|A subscription such as publisher.Changed += subscriber.OnChanged commonly creates a delegate whose target is subscriber. If the publisher remains rooted, that path can outlive the intended subscriber lifetime. Clearing a local subscriber variable does not remove the subscription. Fix ownership with reliable unsubscription or an appropriate weak-subscription design.
46|With var second = first; first = null;, second can still keep the same instance alive while its reference is live. A field, static cache or normal GCHandle can provide yet another path. Setting null neither forces a collection nor calls Dispose, and compiler liveness may already have ended an unused local's root earlier.
47|If a rooted variable reaches A, then A is reachable regardless of its self-reference. When the last external root path disappears, A → A does not substitute for it. The same reasoning extends to cycles containing many objects; GC traces from roots rather than counting how many incoming edges an object has.
48|For example, ref int element = ref array[3] is a managed by-reference into the array. If that by-reference is live in a reported root location, the containing array must survive. Merely having an interior reference stored in an otherwise unreachable graph does not create an independent root. Reachability still starts from actual roots.
49|The collector can associate the interior reference with its containing object, move the object when permitted, and update the reference with the same relative offset. A fixed block or another pinning mechanism adds a movement constraint. Do not equate 'keeps its containing object alive' with 'must preserve the object's absolute address.'
50|The compiler produces GC information while generating machine code; it does not run its optimizer anew during each GC. Later, the runtime reads that information for the current instruction position to find live references. Dead-code elimination and reference-liveness reporting are different compiler responsibilities. AOT compilation is ahead-of-time, rather than a component of JIT execution.
51|For example, after the last necessary use of an object, optimized code may no longer report its local as a root even if more statements remain in the same braces. This need not mean the allocation was eliminated from the compiled program. When native-resource lifetime genuinely requires later liveness, GC.KeepAlive is the relevant explicit lifetime tool.
52|In an interop pattern, place GC.KeepAlive(owner) after the operation that requires owner to remain alive. The point is to stop early loss of the managed lifetime, not to stabilize a buffer's address. If native code needs a stable address, an appropriate pin or other ownership mechanism is needed in addition.
53|Method dispatch means selecting the method implementation to execute, including virtual-call behavior. The object's MethodTable pointer leads to shared runtime type data, not a separate full copy of that data in every instance. 'Type layout' concerns sizes and field/reference organization; it is one aspect of type information, not the whole MethodTable's purpose.
54|In the CLR implementations discussed, GCDesc information for types needing it is associated with the MethodTable and stored immediately before it, rather than before every object. The same broad design exists in .NET Framework, though details vary. GCDesc describes where managed references are, not the complete layout, names and values of every field.
55|Imagine a method local points to an Order instance. GCInfo helps find the local/root in compiled execution; then Order's type-associated reference layout helps find fields pointing to its Customer and items. These two metadata sources cooperate. Neither is the mark stack, and GCDesc is not simply another name for MethodTable.
56|A byte value that happens to look like part of an address is still data, not a managed reference. An object array contains references that can extend the reachable graph. An array of value types with reference fields also needs tracing, so the distinction is the element's reference layout, not simply 'class versus struct' as a label.
57|A struct is a value type, but a field of type string is still a reference to a string object. Copying that struct copies the reference value as part of the value; it does not clone the string. The containing array is a heap object whose embedded reference fields GC must trace using the element layout.
58|A write barrier can record that an old heap region may contain a reference to a young object. Later young collection scans the relevant areas instead of the entire old heap. A card table does not locate planned plug destinations like a brick table, and a dirty card is not a liveness mark for every object it overlaps.
59|A small object can share a card with neighbors, and a large object can span many cards. The collector needs enough boundary/type information to scan valid reference fields in the range. This explains why a region-level dirty record cannot directly answer 'which object just became live?' without further reference processing.
60|During a coordinated pause, compiler GC information and runtime stack/register handling identify roots at the current execution positions. Background collection uses additional protocols for evolving roots and allocations. There is no ordinary heap write barrier that marks a card for every register assignment, and a barrier does not prohibit GC from revisiting the recorded region.
61|The native call stack holds return addresses and frames for executing native/machine-code calls. The mark stack is the collector's explicit traversal worklist. Separately, a mark array/bitmap records discovered liveness; popping a work item does not remove the object's liveness mark or mean its finalizer is ready.
62|A long chain such as A → B → C and onward could require huge recursive depth. An explicit worklist gives the collector control over storage and recovery. It is still finite, so overflow handling remains necessary; avoiding recursive calls is not a promise that an arbitrarily large graph needs no extra traversal bookkeeping.
63|In a cycle A → B → A, once A is marked, reaching it from B need not start the whole traversal again. Marking is not the act that promotes an object to the next generation. During concurrent GC, changed outgoing references can require special rescanning, even though the source object's liveness has already been established.
64|A useful distinction is 'what we know is live' versus 'what we still need to examine.' The mark stack is the latter. Some GC algorithms also use address-ordered survivor information for planning, which should not be confused with a native call stack. Structure names and representations can vary across GC versions and collection modes.
65|Overflow cannot safely mean 'stop marking and assume remaining objects are dead.' The implementation must preserve or reconstruct enough work to finish discovering the reachable graph, potentially with rescanning. The exact recovery algorithm is an internals detail. It trades extra work for correctness rather than turning remaining references into weak references.
66|Only after the necessary traversal and runtime special processing can the collector decide which objects may be reclaimed for that collection. This includes accounting for finalization and concurrent changes. During background marking, new objects and changed references follow the runtime's allocation/barrier protocol; an unfinished mark state must not be interpreted as a free-space map.
67|A million live objects linked by references generally require more tracing than a small live set, even if both processes reserved the same address range. Primitive payload bytes do not each create a graph edge. Profiling should distinguish live graph size, allocation rate and fragmentation, because they affect different parts of GC cost.
68|For example, GC scans A, then the application changes A.Child. If that change matters to liveness, the collector must not miss the new target just because it already visited A. Tracking plus coordination closes this gap. Background GC still has pauses; 'concurrent' does not mean every phase can ignore application mutations.
69|Suppose rooted A references B, GC marks B, and then A.Child is set to null with no other path to B. B may stay marked for this cycle even though it is now garbage. GC normally does not erase the mark and recursively subtract references. Keeping B until a later collection is safe; reclaiming an unrecognized live object would not be.
70|The collector is not reference counting: one edge disappearing does not prove that all other paths disappeared. Even if none remain, retaining an earlier mark is permitted for this collection. This is the key reason a dirty-region revisit does not promise to discover and immediately remove all floating garbage.
71|For a concrete race, A was scanned while A.Child was null; another valid path still held B, then code assigned A.Child = B. Tracking allows the collector to revisit relevant references without rebuilding the entire graph from every root for each write. B was not magically obtained from unreachable bytes; the assignment had a valid source reference.
72|If C.Member is a heap reference field, the write changes memory inside C, so that source location is what region-based tracking records. B need not occupy the same card or generation. GC can later inspect the updated field and discover B. A write barrier records/maintains information; it is not a wall that prevents rescanning.
73|A dirty region tells GC where references may need re-examination, not that every resident object now has a root. The marking algorithm considers its live-source and rescan rules, then traces discovered targets. It does not have to trace every root separately for each object in the region to ask whether that object is live.
74|The code C.Member = B requires a valid way to obtain B, such as a live local or another accessible field. If literally no such reachable path exists, ordinary safe code cannot just rediscover the instance by guessing its old address. A weak reference is a special coordinated retrieval mechanism, not a loophole allowing arbitrary references to reclaimed objects.
75|Consider a live object with a changed field: its mark may already be set and its card may now be dirty. Conversely, a previously marked object can lose its last reference yet keep its mark for this cycle. These independent facts are why 'unmarked and dirty' is not itself a complete reachability explanation.
76|For example, adjacent surviving objects A, B and C can form one plug, with dead gaps before and after. A planned displacement can describe their movement as a unit when permitted. A pinned survivor can constrain plug organization. A plug is not a generation, and its tree/index structures are distinct from the application's object graph.
77|If survivor addresses are in order, planning can recognize where one run ends and a dead gap begins. That supports plug construction and destination calculations. It does not guarantee that every implementation stores the same kind of mark list, nor does it determine the order in which unrelated finalizers execute.
78|Think of a brick as an address-region lookup aid: given a reference address, the collector needs to find the applicable plug information efficiently in the relevant algorithm. A card table answers a different question about possibly changed reference regions. Updating either kind of bookkeeping is not a substitute for relocating the actual root or field reference.
79|A brick index narrows the search by address region; plug-tree information organizes the plug records needed by that algorithm. They should not be treated as one table where changing either automatically repairs every pointer. Avoid making a universal claim about which phase rewrites every entry: the precise maintenance protocol depends on the implementation and GC path.
80|A pending object fitting in one gap says little about the rest of the heap. Many small holes, memory pressure or opportunities to reduce committed space can change the decision. Compaction has a cost too, so there is no rule that pressure always means compact everything; planning balances expected benefit and constraints.
81|For example, copying many megabytes of survivors may cost more than keeping them in place and reusing large existing gaps. Sweeping still needs valid free-space bookkeeping and coordination. A collection may sweep one area while compacting another, so the decision need not apply identically to SOH, LOH and pinned areas.
82|Two neighboring dead blocks can form one larger usable gap, but two gaps separated by a live object cannot become a contiguous block without moving that object. This matters when an allocation fails despite enough total free bytes. Free-space coalescing is not the same operation as calling the dead object's finalizer.
83|A finalizable object needing its finalizer cannot simply be reclaimed as an ordinary dead gap. Finalization processing retains it appropriately and the finalizer thread executes the cleanup body later. That body may explicitly call Dispose(false), but neither the sweeping algorithm nor the GC automatically invokes public Dispose because IDisposable is implemented.
84|For example, a background sweeper must not let an allocating thread consume a block whose free-space representation is still being constructed or modified unsafely. The coordination concerns allocator data and ownership of reusable space. It is not a requirement for application developers to put locks around every new expression.
85|For example, a stack local and A.Child can both refer to the same moving B; both must be valid afterward. Normal handles and relevant surviving weak handles also need correct target references. The compiler/runtime preserve and update reported register roots appropriately during suspension. Object type metadata is not a central replacement for these actual references.
86|If the containing object's new base is 2000, an interior pointer previously 16 bytes into it must refer to 2016, using simplified illustrative addresses. This is one reason GC must locate the containing object or plug. The interior reference can keep the object alive without requiring its original absolute address to remain fixed.
87|The background-GC setting does not make .NET's moving compaction fully concurrent. The runtime suspends appropriate managed execution while it performs movement and repairs references. Otherwise an application could observe inconsistent old and new locations. Concurrent marking/sweeping mechanisms solve different overlap problems and should not be generalized to every phase.
88|The root/reference graph remains valid because the previous moving collection repaired the tracked references before application execution continued. The next mark phase therefore does not need stale brick or plug data to 'guess' where objects went. Such indexes support internal algorithms; they are not the sole source of truth for all application reference values.
89|For a class reference assignment, obj.Field now points to the same target as other; it does not copy the target's fields into obj. The target can later move during a GC, and the collector then maintains references. Struct assignment copies a value and may copy reference-valued fields inside that value, which is a different operation.
90|The collection still needs to identify survivors and safely make dead gaps reusable. 'No relocation for unchanged addresses' does not mean 'no planning or marking needed.' If another area in the same collection is compacted, references to objects moved there still need appropriate treatment even though this particular area's survivors stayed in place.
91|A fixed statement or pinned GCHandle can establish a pin; appropriate APIs can also allocate pinned storage. When the pin ends, the object may move in a later moving collection. A normal GCHandle or GC.KeepAlive keeps a target alive but does not provide the same stable-address guarantee.
92|Imagine two pinned survivors with dead space around them. The collector cannot freely slide those survivors together to combine all the gaps. The POH reduces this problem for supported pinned allocations, but it does not retroactively move existing SOH/LOH pins into the POH or eliminate fragmentation in every area.
93|For example, GCHandle.Alloc(existingArray, GCHandleType.Pinned) pins that already allocated array where it is. By contrast, supported pinned allocation APIs can choose POH storage from the start. Pinning and promotion are separate: being immovable does not universally mean the object must remain generation 0 forever.
94|For a suitable reference-free array, GC.AllocateArray<byte>(length, pinned: true) is an example of an explicitly pinned allocation API. This is different from pinning a preexisting array with fixed. The POH still needs collection and space management; separating pinned allocations does not promise zero memory retention or zero fragmentation.
95|After leaving the block, a raw native pointer obtained inside it must not be used as though the managed object is still pinned. Native code retaining a pointer requires an ownership/lifetime scheme that covers its entire use. Keeping a managed reference alive alone prevents collection but does not by itself prevent movement.
96|For example, GCHandle h = GCHandle.Alloc(item, GCHandleType.Normal) adds a strong handle root until h.Free(). Setting the original item variable to null does not remove that root. The target can move; the runtime updates the handle's target information. Normal does not mean a weak reference or a pinned native address.
97|A GCHandle is a value-type wrapper representing a runtime handle, not a string reference and not the target stored inline. GCHandle.ToIntPtr can provide an opaque token for passing that handle through native code; the token is not permission to dereference it as the object's raw memory address. Access the target through the supported handle API.
98|Free the handle exactly according to its ownership, often with try/finally, once native use is finished. Copies of a GCHandle struct do not create independent target ownership automatically; double-freeing through aliases is also unsafe. A pinned root can keep a large graph or buffer around even when no application local still refers to it.
99|h.Free() removes that handle entry, not every other reference to the target. If a static cache still contains item, the target remains alive. If no path remains, GC can handle reclamation under normal policy, possibly after finalization. Calling GC.Collect is not the manual counterpart of freeing each handle.
100|Both weak-reference forms can lose their targets. If weak.TryGetTarget(out var target) succeeds, target is an ordinary strong reference while it remains live. That temporary strong reference can now extend the object's lifetime; the weak reference itself has not changed into a permanently strong one.
101|A short weak reference is cleared when its target is identified for the relevant reclamation/finalization processing, before the original finalization runs. A resurrection-tracking weak reference can continue to report the object afterward until later collection clears it. The flag does not re-register the finalizer, create a root, or guarantee actual resurrection.
102|The clearing event precedes that finalization, but your observation can occur later, after the finalizer has or has not run. There is no contradiction between these statements. Therefore false is not a finalizer-completed signal or proof that memory was returned to Windows. Null targets, explicit target changes and unusual reuse scenarios can further affect observations.
103|Removing a local strong reference does not synchronously clear weak references. Both true and false are possible depending on lifetime, other paths and collection timing. In the ordinary initial short-weak scenario, true does not mean the finalizer already ran. Avoid using weak-reference polling as a resource-cleanup ordering mechanism.
104|Compare a normal Dictionary: a reachable dictionary strongly retains its keys and values. A reachable ConditionalWeakTable instead uses dependent-lifetime associations; the key needs an independent reachable path. The table's own lifetime still matters too, so do not say association behavior is independent of whether the table instance remains alive.
105|Otherwise every value that pointed back to its key would defeat the purpose of weak-key storage. If an unrelated root independently references V, then V's ordinary field reference to K can keep K alive; that is a different external path. The isolated table association by itself is what must not establish self-sustaining liveness.
106|For example, rooted K1 activates its association with V1; V1 has an ordinary field referencing K2; K2 then activates V2. A single pass that checked K2 before discovering V1's reference could miss that chain. Processing to a stable result handles these dependencies without treating all table keys as unconditional roots.
107|For class Example, ~Example() { ... } is C# finalizer syntax, compiled into the runtime Finalize pattern. You cannot make a class implement IDisposable without satisfying its interface contract, whether directly or through inherited/explicit implementation. Adding Dispose does not create a finalizer, and removing a finalizer does not remove the need for explicit cleanup of owned resources.
108|Do not confuse the initial registration mechanism with later readiness for finalization. When a GC finds an otherwise unreachable registered object that still needs finalization, it arranges for finalizer execution and preserves the needed graph. Calling SuppressFinalize can make that execution unnecessary without a promise that the registration's internal storage is physically erased immediately.
109|The finalizer may read fields or invoke code using referenced objects, so reclaiming those objects' managed storage too early would break memory safety. However, preserving storage does not guarantee their own finalizers have not run. Objects independently rooted elsewhere also stay alive through those separate paths. Retention protects access to memory, not a universal resource-cleanup order.
110|Suppose A's finalizer reaches B through a field. B's managed instance remains safely accessible as required, but B may already have closed its native handle in its own finalizer. That is an already-cleaned-up resource issue, not necessarily a dangling managed reference. Prefer explicit disposal for ordered ownership and SafeHandle for directly owned native handles.
111|If no caller disposes a managed wrapper with no finalizer, GC can still reclaim its managed storage when unreachable, but that is not execution of its cleanup contract. A finalizer body only calls Dispose if the developer wrote such a call. using is compiler-generated try/finally-style disposal, not the GC secretly calling the interface.
112|Typical shape: public Dispose() calls Dispose(true), then GC.SuppressFinalize(this); ~Owner() calls Dispose(false). true means explicit cleanup may dispose owned managed resources as well as release unmanaged ownership. false avoids depending on other managed objects' cleanup state. The finalizer is a separate method outside Dispose, not a method declaration nested inside it.
113|protected means the method is available to the class and derived classes, not arbitrary callers. virtual means a derived class can override it to clean up additional owned resources, normally calling base.Dispose(disposing). public on its own is only an accessibility modifier: a public ordinary method is not overridable unless the appropriate virtual/abstract/override mechanism applies.
114|If explicit disposal already released the native resource, later finalization would be unnecessary work and could be dangerous in a badly written release routine. Suppression targets that instance's finalizer, not all collections or every object of its type. The object can still become unreachable and be collected normally. A class with no effective finalizer ordinarily does not need this call for itself.
115|Suppose the caller executes owner.Dispose() twice. SuppressFinalize prevents finalizer work; it does not prevent the second explicit call. A disposed flag or a stronger release-once ownership mechanism ensures the resource is not released twice. Forgetting to call Dispose is a separate fallback-finalization problem, not the main reason to guard repeated explicit disposal.
116|If a field is a SafeHandle, it already encapsulates native ownership and a finalization fallback. Your wrapper can dispose it explicitly without necessarily adding another finalizer. Removing both a custom finalizer and SuppressFinalize is often right when no direct unmanaged ownership requires that finalizer; blindly removing a necessary fallback from raw-handle ownership is different.
117|A file handle number can be reused by the OS after close. A stale second close can target invalid or even newly reassigned ownership, so 'it only wastes time' is unsafe reasoning. Use SafeHandle where possible, and design disposal ownership carefully. A plain unsynchronized disposed boolean alone does not settle every race between concurrent callers.
118|For example, a finalizer could assign a static field to this, creating a new strong path. The instance is now reachable through that root, even though it was previously unreachable and queued. Its fields or external resources may already be partly cleaned up, which makes resurrection difficult to use correctly. 'Finalizer ran' is not the definition of unreachable.
119|GC.ReRegisterForFinalize(obj) is an explicit request for another finalization opportunity when appropriate. trackResurrection: true only changes a weak reference's tracking behavior; it does not call this API. A resurrected instance may therefore be used and later collected without its finalizer running a second time if it was not re-registered.
120|After finalization, a later collection can reclaim the object if no strong path keeps it alive and no further finalization requirement applies. A static resurrection path can prevent that reclamation. Finalizer completion is therefore neither immediate deletion nor a guaranteed transition to unreachability; the reference graph still determines reachability.
121|In a controlled diagnostic demonstration, GC.Collect(); GC.WaitForPendingFinalizers(); GC.Collect(); separates discovery, finalizer waiting and later reclamation. This is not a recommendation to insert that sequence into routine request handling. WaitForPendingFinalizers is called by developer code and can block while pending finalizers execute; it does not itself discover all unreachable objects.
122|If a finalizer waits on a lock whose owner is waiting for finalization, cleanup can stall or deadlock. Pending finalizable objects and their reachable graphs can accumulate. Keeping finalizers short and focused on directly owned unmanaged resources reduces this risk. A large finalization backlog can be a retention cause even with otherwise functioning GC.
123|An escaping exception means it is not successfully handled before leaving the finalizer. Merely writing a try/catch somewhere does not ensure every catastrophic failure is recoverable. Ordinary cleanup should not throw out of a finalizer; rely on reliable ownership abstractions rather than complex fallback code. Process termination policy is a reason finalizers must remain simple.
124|The JIT's earlier compilation establishes GC reporting and interruptibility information. Later, the runtime coordinates thread transitions/suspension and consults that information; it does not ask the optimizer to compile the stack again. In modern .NET these execution-engine responsibilities live within CoreCLR, rather than requiring a separate application DLL named 'execution engine.'
125|The runtime must obtain a position where the compiler can accurately report and update live references. 'Partially interruptible' describes where that information supports suspension, not a developer putting Thread.Sleep halfway through a method. A fully interruptible region provides broader reporting coverage; it still relies on metadata rather than guessing which machine words are pointers.
126|A blocking server collection can use several GC threads in parallel while application threads are paused. Background marking can overlap application work, potentially also using multiple workers. Consequently, seeing many GC threads does not prove concurrency with your request threads, and seeing a GC wait frame alone does not identify which complete GC algorithm is active.
127|Generation 0 and 1 work can happen as foreground pauses during that background generation 2 collection. Root coordination and final portions also require pauses. So 'background GC applies to generation 2' does not mean a full-collection interval excludes younger objects or that application allocation must stop for the whole interval.
128|A pause allows the runtime to present a consistent set of reference locations and planned destinations. Threads in native/preemptive states and runtime transition machinery can appear differently in a dump, so not every OS thread has to show an identical GC wait frame. The important guarantee concerns safe managed-reference handling during the moving operation.
129|Server GC generally organizes heaps and workers for throughput-oriented workloads; workstation GC generally emphasizes other usage patterns and resource tradeoffs. Either can have background support in appropriate runtime versions. Historical concurrent GC is not identical to background GC: an important improvement was allowing foreground young collections during background generation 2 work.
130|More allocation capacity and heap organization can reduce collection frequency or allow more parallel GC work, increasing throughput in suitable workloads while retaining more capacity. That memory increase is not proof every object was duplicated or leaked. Compare live object retention, committed space and workload limits before deciding whether the change is acceptable.
131|CPU affinity, container/job CPU limits, explicit heap-count settings and adaptive behavior can affect what the runtime uses. Some modern policies can also adjust server heap organization. Separately, foreground and background worker counts can differ from heap count. Use system/runtime configuration evidence to determine processor availability instead of deriving it from one heap number.
132|If configuration A completes 1,000 requests/second and B completes 1,150 under the same load conditions, B has 15% higher measured throughput. It can still consume more memory or have worse high-percentile latency. A good choice depends on whether those resource and response-time tradeoffs meet the application's goals.
133|For example, the collector may trace concurrently while requests run, with short pauses for necessary coordination. Total elapsed duration includes that overlapping work. It also need not equal total GC CPU time when several workers run in parallel. Always distinguish elapsed collection time, accumulated CPU time and application pause time.
134|A smaller number of long pauses can hurt p99 latency more than many short pauses. A request can also take 500 ms while GC pauses account for only 10 ms, leaving locks, I/O, CPU scheduling or other work to investigate. Avoid attributing every slow request to the nearest GC event.
135|Measure at least allocation rate, live/committed memory, throughput and response-time/GC-pause distributions. Warm-up matters because JIT compilation, caching and startup allocations can distort a short test. Repeat runs and keep machine/workload conditions comparable. Accepting more memory for better throughput is a workload decision, not an automatic win or loss.
136|A forced full collection can scan survivors and introduce blocking work even when the adaptive collector would wait. It cannot reclaim a cache entry that remains strongly rooted. If the underlying issue is an unbounded static collection, fixing its retention policy matters more than forcing GC more frequently. Use measurements to distinguish retention from allocation pressure.
137|Examples include a controlled experiment to study weak/finalizable lifetimes or a measured application lifecycle transition after unusually large temporary work. Consider whether the normal collector already responds adequately and whether the pause is acceptable. Explicit GC is not the normal mechanism for disposing files or freeing a GCHandle's target one object at a time.
138|The parameterless call requests an immediate full blocking collection. Overloads expose generation, collection mode, blocking and compaction requests, but runtime state affects supported nonblocking behavior. Collection still needs tracing before reclamation. A nonblocking request is not permission to perform moving compaction while application threads mutate references freely.
139|For example, find a large dictionary type, inspect its instances and follow paths to roots to see whether a static session map retains it. Large reachable graph size does not mean millions of roots exist: a single static field can retain millions of descendants. Review object ownership and expected cache/session lifetimes before concluding the runtime is leaking.
140|A bucket array may be only a few megabytes itself but reach hundreds of megabytes of entries and their object graphs. A graph-size command can therefore disagree with a shallow-size statistics column without either being wrong. Inclusive size may count shared descendants reached through this object; that is not automatically memory exclusively retained by it.
141|Suppose A and B both reference C. Removing A does not make C collectible while rooted B still reaches it. Therefore the bytes reachable from A can exceed the bytes exclusively retained through A. Some views use spanning-tree attribution rather than exact dominator analysis, so interpret percentages and counts using the tool's stated semantics.
142|For example, WinDbg's native Heap usage category is not a direct total of managed GC objects. A .dmp file's on-disk length also does not equal virtual reservation, resident RAM or shallow managed object bytes. Use appropriate committed-memory and heap views, and remember that large reserved ranges can have little or no backing allocated.
143|The reserved addresses belong to this process's virtual address map, not a permanently reserved set of physical RAM chips. Another process can use the same numerical virtual addresses in its own map without conflict. Reserving a large range does not by itself allocate that amount of resident RAM or allow your code to write to every page.
144|Decommit releases commitment for pages, so those pages are no longer usable for ordinary data access until recommitted. The process can still retain the numerical virtual address range. Physical backing released from those pages can serve another purpose while the address reservation stays with the process. Releasing the reservation is a separate step.
145|Committed virtual memory has backing/storage obligations, but pages can be resident, paged out or not yet physically instantiated depending on the mapping and OS behavior. The working set concerns resident pages; it is not the same total as committed space. Reserved address space is another larger category that has not necessarily been committed at all.
